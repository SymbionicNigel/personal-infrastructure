One motif, three times: the scattered descriptor

Reading the whole tree, the same shape recurs across the infra layers: a domain entity (a tailnet device, a postgres role, a stack service’s env) whose identity is smeared across three or four files, held together not by code but by a hand-maintained “to add one, edit these N places” comment checklist. Each is a shallow arrangement — the interface (the checklist you must remember) is as big as the thing itself.

The north star already exists in this repo. iris/app/nav.ts defines pages once as a PAGES tree, and both the route table (routes.ts) and the breadcrumb navigation (useBreadcrumbs) are derived from it. That is a deep module: one small registry, many consumers, add-a-page-is-one-edit. The three candidates below are the same move applied to the infra layers, which haven’t adopted it yet.

A · A devices table for the tailnet

Strong

Files

  • linode/modules/tailnet/main.tf
  • linode/modules/tailnet/acl.hujson
  • linode/environments/production/outputs.tf
  • homelab/scripts/pi-firstrun.sh:12

Problem

A device’s identity lives in four places: three copy-pasted tailscale_tailnet_key resources (differing only in description + tags), a hand-kept tagOwners block, per-device outputs, and — worst — the Pi’s advertised route is hardcoded as 192.168.18.0/24 in pi-firstrun.sh, re-stating var.HOME_LAN_CIDR with only a “must stay in sync … or the route won’t auto-approve” comment holding them together. Change the CIDR in Terraform and the Pi silently advertises a route that never auto-approves.

Solution

Define each device once — { tag, description, advertise_routes, ssh } — and derive the keys (for_each), tagOwners, autoApprovers, and outputs from it. Because the advertised route is now a column, stage it into the Pi payload from Terraform (the way the auth key already is), so pi-firstrun.sh reads it from a file instead of hardcoding it. The CIDR exists once; drift becomes impossible rather than merely discouraged.

Benefits

  • Leverage: a new device / changed route is one map edit, not four.
  • Locality: tag, key, and routes for a device sit on one row.
  • Test surface: the map becomes assertable — a plan/policy check over one table replaces eyeballing three near-identical resources for divergence.

Before

acl.hujson   tagOwners: dokploy, mc-compute, mc-gateway
             autoApprovers: 192.168.18.0/24 -> mc-gateway
main.tf      key "cloud"   } three near-identical
             key "compute" } tailscale_tailnet_key
             key "gateway" } resources
outputs.tf   compute_auth_key, gateway_auth_key
pi-firstrun  HOME_LAN_CIDR=192.168.18.0/24   # dup of var

After

locals.devices = {
  dokploy    = { tag=..., routes=[],              ssh=true }
  mc-compute = { tag=..., routes=[] }
  mc-gateway = { tag=..., routes=[var.HOME_LAN_CIDR] }
}
keys / tagOwners / autoApprovers / outputs
                       = derived from devices
pi route staged from TF -> read from file

Deletion test: collapsing the resources + owner list into the map concentrates complexity into one readable place. ADR-0001-safe: stays inside the tailnet module / Production Layer; doesn’t touch the Dokploy-Layer split.

B · Derive the postgres --set role bindings instead of listing them

Strong

Files

  • postgres/scripts/entrypoint.sh
  • postgres/scripts/reconcile-roles.sql
  • .secrets/.chezmoitemplates/postgres-roles-env

Problem

The same scattered-descriptor shape. reconcile-roles.sql’s own header spells out the ritual: “Adding a role: 1. add a POSTGRES_<NAME>_PASSWORD; 2. add a --set=<name>_password=… binding to entrypoint.sh; 3. add a create-then-alter pair.” Step 2 is the fragile one — entrypoint.sh hardcodes --set=astarte_password=… --set=iris_ro_password=…, one line per role. Add a role and forget step 2 and the SQL fails at :'newrole_password' — at container start, i.e. a fail-closed deploy outage.

Solution

The role→password convention is already regular (POSTGRES_<NAME>_PASSWORD → :'<name>_password'). Generate the --set bindings in entrypoint.sh by looping over the matching env vars, lowercasing the <NAME>. Step 2 of the checklist disappears; the SQL file becomes the single source of truth for which roles exist, and passwords wire themselves.

Benefits

  • Removes a fail-closed foot-gun: the highest-consequence step (a missed binding = start-time crash) stops being manual.
  • Locality: “what roles exist” is answered by the SQL alone, not SQL × shell.

Aligns with your recorded fail-closed preference — this keeps the loud failure but removes the easy way to trip it.

# entrypoint.sh — before (hand-listed, drifts from the SQL)
psql ... --set=astarte_password="$POSTGRES_ASTARTE_PASSWORD" \
         --set=iris_ro_password="$POSTGRES_IRIS_RO_PASSWORD" ...

# after — derived from the POSTGRES_*_PASSWORD convention
args=(); for v in "${!POSTGRES_@}"; do
  case "$v" in *_PASSWORD) n=${v#POSTGRES_}; n=${n%_PASSWORD}
    args+=(--set="${n,,}_password=${!v}") ;; esac
done
psql ... "${args[@]}" ...

C · A per-service env registry for the Dokploy Layer

Worth exploring

Files

  • linode/environments/dokploy/main.tf
  • docs/guides/env-wiring.md

Problem

The third instance of the motif, and the softest. Each service’s env is a separate data "dotenv" block plus a hand-ordered entry in the merge(...) whose last-wins collision semantics are load-bearing and explained only in a comment. Adding a service’s env means: a new .env.*.prod, a new data block, and remembering where it goes in the merge order.

Solution & caution

A for_each over a service→env-file map would collapse the repeated data blocks. But the collision ordering and the deliberate iris_typegen exclusion are real domain rules, not accidents — a naive for_each that flattens them would move complexity, not remove it. Worth exploring only if the explicit precedence is preserved as data (e.g. an ordered list with intent, not alphabetical for_each).

⚠︎ Adjacent to ADR-0002 (routing stays in compose labels, not Terraform). This candidate is about env aggregation, not routing, so it doesn’t contradict the ADR — but it lives in the same compose/Terraform seam the ADR deliberately keeps thin. Tread lightly; don’t let env-wiring pull routing back into TF.

D · The duplicated @@AUTHORIZED_KEYS@@ render loop

Speculative

Files

  • homelab/scripts/build-thinkcentre-iso.sh:59
  • homelab/scripts/stage-pi-sd.sh:39

A byte-identical ~10-line marker-expansion loop lives in both staging scripts. Two callers is a real seam, not a hypothetical one — but lifting it into a shared lib.sh with a single function bumps directly against your recorded preferences (colocate a lone helper; no single-function util files). Left speculative on purpose: revisit only if a third payload-rendering caller appears or the loop grows.

Top recommendation

Start with A — the tailnet devices table.

It’s the clearest instance of the motif and the one with an active hot spot (this branch). It gives the domain concept “a device on the tailnet” a single home, collapses three copy-pasted key resources plus the hand-kept tagOwners and outputs into one derivable table, and — because routes become a column — dissolves the HOME_LAN_CIDR drift for free. B is a close second and cheaper (one shell loop) with a real safety payoff; do it next. C needs care around its load-bearing ordering, and D is parked against your stated preferences. Across all four, the target state is the one iris already demonstrates: one descriptor in, everything derived out.
